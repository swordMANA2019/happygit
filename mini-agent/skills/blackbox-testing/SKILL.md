# 黑盒自测

目标：**不靠"我看着没问题"，而靠"我运行过、看到了结果"** 来下结论。
这里没有现成的测试工具可用——**测试环境要你自己根据当前问题搭**，用完即弃。思路比工具重要。

## 思路：先问"怎样才能亲眼看到它出问题/不出问题"

1. **这次改动要保证什么？** 把它说成一句可观察的话。
   例："流式输出时模型一直在吐字就不该超时，卡死 N 秒才该超时"；"训练脚本能跑完 2 步并写出 checkpoint"；"输入为空时报清楚的错、退出码非 0"。
2. **要观察到这个行为，缺什么条件？** 然后**自己造出那个条件**：
   - 缺一个会出问题的外部服务 → 自己写一个几十行的"桩服务"（Python 标准库 `http.server` / Node `http`，哪个能用就用哪个），让它按你要的方式表现：正常、很慢、中途卡死、返回 500/429、返回畸形数据……
   - 缺真实数据 → 造 5~20 条格式一致的假数据。
   - 缺 GPU / 大模型 / 联网 → 缩成最小配置（小模型或随机初始化、`max_steps=2`、CPU）。
   - 缺外部命令 → 写一个假的同名脚本放进 PATH 的临时目录，记录它被怎样调用。
3. **让被测代码连上你搭的环境**（改环境变量/配置/参数指向它，**不要改项目代码去迁就测试**）。
4. **每个场景先写期望，再运行，再对照实际输出。** 至少 1 个正常路径 + 1 个失败/边界路径。
   对"用桩服务"的场景，让桩服务记录收到的请求，用来断言被测代码发出的请求对不对。
5. **失败要追根：** 是项目代码的缺陷 → 修项目代码并**重跑同一场景**；是你的测试写错/环境问题 → 改测试或换更小的环境。不要放宽判断去让它变绿。

## 一个完整的例子（思路示范，不是模板）

改动：给"调用 LLM 的客户端"加了超时和重试。要验证 3 件事：①持续输出的慢响应不该超时 ②卡死的响应该超时并重试 ③网关返回 500 会重试后放弃。
做法：自己写一个小桩服务，按请求次数/模式分别返回"每 1 秒吐一块"、"吐一块后不再发数据"、"直接 500"；
把客户端的 base URL 指到它；跑三个场景，看日志和退出码；再看桩服务记录的请求次数是否等于预期的重试次数。
第 ② 个场景一开始发现"被截断的半截回复被当成完整答案"——这就是靠自己搭环境才测出来的缺陷。

## 工作目录约定

- 所有测试脚本、桩服务、假数据只放在 `.agent/scratch/` 下（write_file 可以直接写；这里的文件不算用户的改动）。
- 桩服务/长命令用 `run_command` 的 `background=true` 启动，`job_output` 读到它就绪的输出；用完必须 `stop_job`。
- 端口用 0（让系统挑空闲端口）并把实际端口打印出来，避免冲突。

## 按场景的提示

- **训练 / 微调脚本：** 缩到几十秒跑通——能启动 → loss 是有限数 → 输出目录有 checkpoint/日志 → 能重新加载并推理一次；
  再测一个失败路径（数据文件不存在 / 字段缺失，报错是否清楚、退出码是否非 0）。
- **命令行工具：** 用真实参数运行，检查 stdout/输出文件的具体内容；缺参数、坏输入时检查退出码和报错。
- **库函数 / 纯逻辑：** 写小脚本直接调用，覆盖典型、空、边界、非法输入，打印实际返回值再对比。
- **文件产出（PPT/Word/Excel/图片）：** 生成后读回来核对内容，而不是只看"生成成功"。
- **数据库：** 优先用 SQLite 临时文件/内存库代替；确实需要真库就说明"未测"。

## 自检清单（下结论前过一遍）

- [ ] 我真的运行过命令并看到了输出（不是"应该能跑"）？
- [ ] 有失败/边界场景吗？
- [ ] 发现的问题我修了并**重跑**了吗？
- [ ] 桩服务等后台进程都 stop_job 了？
- [ ] 汇报里写清了：测了什么、没测什么、为什么没测？
